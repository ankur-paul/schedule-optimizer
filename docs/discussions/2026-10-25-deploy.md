# Deploying Lattice (discussion, 25 Oct 2026)

Roadmap idea #8. It picks up the 22 Oct notes ([`2026-10-22-deployment.md`](2026-10-22-deployment.md)), which still
hold the solve-time measurements, the Lambda cost maths and the hosts turned down. Four rounds of questions; the plan
below is what came out of them, and the grilling notes at the end record the reasons and the options turned down.

## Plan

### What it is

A public demo that a few real institutes can try, built properly: its own domain, a production Supabase project,
CI before every deploy. Free tiers plus the domain, no monthly bills. No deadline. The Anthropic spend limit and the
AWS Free plan's end date are the operator's to handle and stay out of the tickets.

### Where things run

| Part | Where | Address |
|---|---|---|
| Web app (static Vite build) | Cloudflare Pages | `https://uselattice.app`; `www` redirects to it |
| Solver (`/health`, `/solve`) | AWS Lambda, Mumbai, 3,008 MB, `SOLVER_WORKERS=2` | its raw Function URL |
| Assistant (`/agent`) | AWS Lambda, Mumbai, 512 MB, same image | its raw Function URL |
| Accounts, institutes, timetables | A new free Supabase project, Mumbai | `https://<ref>.supabase.co` |
| Sign-in email | Resend free plan, as `Lattice <no-reply@uselattice.app>` | — |
| `privacy@uselattice.app` | Cloudflare Email Routing, forwarded to the operator's inbox | — |

- **Domain:** `uselattice.app`, registered at Name.com on 24 Oct 2026 (expires 24 Oct 2027; turn on auto-renew). Its
  nameservers move to Cloudflare; the registration stays at Name.com. It had only a parking `A` record, no MX or TXT.
  `.app` is HTTPS-only in every browser (HSTS preload).
- **Function URLs, not `api.uselattice.app`:** a custom domain needs CloudFront in front, which cuts requests at
  30 s by default. Only the web app calls these URLs (`VITE_SOLVER_URL`, `VITE_AGENT_URL`). Auth type `NONE`;
  Function URL CORS off, since FastAPI's CORS middleware answers.
- **The solver** goes live at 3,008 MB with 2 workers, the account's cap. The support case for 10,240 MB is not
  approved yet; when it is, raise the memory to about 7 GB and `SOLVER_WORKERS` to 4 in the console, no new build.
- **Email:** Email Routing puts its MX on the domain; Resend uses `send.uselattice.app` for bounces plus a DKIM key.
  One SPF record lists both, and one DMARC record is added. Resend's free plan allows 3,000 emails a month and 100 a
  day; only sign-in links and invites are sent. Catch-all off.

### How a change reaches production

1. **CI** (GitHub Actions) on every push and pull request: `npm ci`, `npm test`, `npx tsc -b`, `npm run build` in
   `web/`; `uv run pytest` in `server/`, including the `supabase` tests against the **dev** project, whose keys are
   GitHub secrets. Third-party actions are pinned to commit SHAs.
2. **Deploy**, on `main` only, after CI passes:
   - check that production has every migration in `supabase/migrations/` (a public `schema_version()` function,
     called with the anon key); stop if not;
   - build one x86_64 image, push it to ECR tagged with the commit SHA (the last 10 kept);
   - `update-function-code` on both functions. Never `update-function-configuration`: the env vars are set by hand;
   - call the Cloudflare Pages **deploy hook**; Pages builds `main` itself (automatic deploys off);
   - **smoke check:** `/health` on both functions (the contract version must match the commit's), and
     `https://uselattice.app/privacy` loads.
3. **Rollback:** a manual *Run workflow* that takes a SHA and points both functions at that image. The web app rolls
   back from the Pages dashboard.
4. **Keep-alive**, a GitHub schedule every 3 days: calls `schema_version()` so the free Supabase project never
   pauses (it pauses after 7 days without activity, which breaks sign-in and every public link), and runs the same
   smoke check. GitHub emails the operator when it fails, so this is the uptime check too. GitHub turns schedules off
   after 60 days without commits; re-enable it then.

### Secrets

- **What GitHub holds:** the dev project's Supabase URL and keys (for CI), the Pages deploy hook URL, and the AWS
  role's ARN (not secret). No production secret. AWS access is through **OIDC**: a role only `main` can assume, which
  can push to one ECR repository and update the code of the two functions.
- **Lambda env vars, set by hand in the console:**
  - solver: `SOLVER_WORKERS`, `CORS_ORIGINS`;
  - agent: `ANTHROPIC_API_KEY`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `CORS_ORIGINS`, `AGENT_MONTHLY_USD`.
  The solver never gets a key it doesn't use. `docs/deploy.md` lists every variable per function.
- **The web app has no secrets.** Its public settings (production Supabase URL and anon key, both Function URLs,
  `VITE_CONTACT_EMAIL=privacy@uselattice.app`) are committed in `web/.env.production`.
- **Production migrations run from the operator's laptop** (`scripts/migrate-prod.sh`): `supabase db push` needs a
  token and the database password, either of which gives full control of production.
- Whoever can deploy code can read the secrets at run time, whatever store holds them. What counts is keeping
  secrets out of GitHub and narrowing who can deploy.

### Code changes before the first deploy

- **Health check:** `HEALTH_TIMEOUT_MS` 1 s → 5 s, since a cold start takes longer. Checked when the site opens,
  not only when step ③ mounts.
- **Solve grace:** `SOLVE_GRACE_MS` 10 s → 15 s.
- **Server caps:** `time_limit_sec ≤ 120`; `/solve` refuses bodies over a size cap, as `/agent` does.
- **`SOLVER_WORKERS`** from the environment (default 8, as now).
- **Contract version:** `shared/contract.json` holds one number; `/health` returns it, and the web app warns when
  the server's differs from its own. Pages and Lambda deploys finish at different times.
- **Request logs:** one line per request (method, path, status, duration). Never bodies or IP addresses.
  CloudWatch keeps them 14 days.
- **Teacher codes to `/solve`:** an imported teacher's id is a slug of the name (`dr-anita-sharma`, T37's note), and
  `/solve` sends ids. It sends the assistant's codes (`T-K3X9Q`, `features/assistant/mask.ts`) instead and maps
  them back in the result, so no name reaches the server.
- **Dockerfile** for `server/` with `uv`, run on Lambda through the AWS Lambda Web Adapter, so the same image runs
  locally with `podman run`. The image carries `web/src/help/*.md` and `shared/`.

### Guards on the open solver

`/solve` stays open, signed in or not, as v1 promised. The caps above, Lambda's 10 concurrent executions and an AWS
Budgets alert emailed at $5 are the guard. Worst case, solves around the clock use the month's free Lambda allowance
in about 4 hours and then about $1.80 an hour of credit.

### Privacy policy v4

Everyone signed in accepts again. It adds:
- our server runs on **Amazon Web Services in Mumbai**;
- **Cloudflare** serves the site and sees visitors' IP addresses;
- **Resend**, a US company, sends sign-in emails and so receives email addresses;
- technical logs (no timetable data) are kept for 14 days.

### Google sign-in

A second OAuth client in the same Google Cloud project, for the production Supabase callback. The consent screen is
published as "Lattice", home `https://uselattice.app`, privacy `https://uselattice.app/privacy`, **no logo** (a logo
starts brand verification).

### Setup and docs

- Scripts for what a CLI can do (`aws`, `wrangler`, `supabase`); a wizard (the `wizard` skill) for the console clicks
  only the operator can make: Cloudflare account and nameservers, Email Routing, Resend, the Supabase project's auth
  settings, the Google console, the Lambda env vars, the GitHub secrets.
- `docs/deploy.md` records the whole setup so it can be redone.
- `PLAN.md`'s *Demo* row becomes *Deploy*. The help screenshots use `https://uselattice.app` instead of
  `https://lattice.example`.

### Not in this pass

- The laptop + Cloudflare Tunnel fallback from 22 Oct.
- Analytics.
- Custom domains for the Function URLs.
- Parameter Store or Secrets Manager.

## Grilling notes

- **Q1 A public demo built properly, on free tiers.** Rejected: a short-lived cohort-only URL on the dev project.
- **Q2 Budget: the domain only.** Supabase Pro ($25/month) would fix pausing and backups; a keep-alive covers
  pausing, and Free keeps no backups, so the policy's "erased within 7 days" stays true. The Anthropic spend limit
  is the operator's.
- **Q3 No deadline.**
- **Q4 Cloudflare over Vercel.** Both host a static build equally well and the app isn't commercial now, so Vercel's
  terms didn't rule it out. Cloudflare won on domain, DNS and `privacy@` forwarding in one free account, and allows
  commercial use if a paid plan comes back.
- **Q5/Q6 Deploy at 3,008 MB now** (the memory increase isn't approved) and raise it later as a setting.
- **Q7 CI gates every deploy, Supabase tests included,** against the dev project.
- **Q8 Nameservers to Cloudflare,** registration stays at Name.com. Found: registered 24 Oct 2026 at Name.com, only a
  parking record.
- **Q9 Raw Function URLs.** Rejected: `api.uselattice.app` through CloudFront.
- **Q10 Resend.** Rejected: Brevo (branding), Amazon SES (sandbox approval).
- **Q11 A new free Supabase project and a 3-day keep-alive.** Rejected: a Cloudflare cron Worker (one more thing to
  deploy). **Q11b** later moved production migrations out of CI to the operator's laptop, so no production database
  credential sits in GitHub; CI only checks they were applied.
- **Q12 x86_64 image, OIDC, deployed by Actions.** Rejected: arm64 (emulated builds on GitHub's x86 runners).
- **Q13 `/solve` stays open with caps and a $5 Budgets alert.** Rejected: a solver behind sign-in (breaks signed-out
  use).
- **Q14 No preview deploys.**
- **Q15 Policy v4 with re-accept.** Found: the policy doesn't say where the server runs and names neither Cloudflare
  nor Resend.
- **Q16 Codes, not ids, to `/solve`.** Found: the policy says names are "replaced by a code", which T37 noted isn't
  true for imported teachers.
- **Q17 All the 22 Oct code changes stay,** less CORS (done in T38) and CI (Q7).
- **Q18 Secrets set by hand in the Lambda console, only on the function that uses them.** Compared: GitHub
  environment secrets written by each deploy (secrets in GitHub; the repo is private, and environments there need
  GitHub Pro), a script from the laptop, Parameter Store (code and IAM for little gain with one operator).
- **Q19 A production OAuth client, consent screen published without a logo.**
- **Q20 Scripts plus a wizard plus `docs/deploy.md`.**
- **Q21 No laptop tunnel fallback.**
- **Q22 Logs without bodies or IPs, 14 days.**
- **Q23 Public web settings committed** in `web/.env.production`.
- **Q24 Pages with the Git connection, automatic deploys off, a deploy hook after CI.** Rejected: `wrangler` from
  Actions (a Cloudflare token in GitHub, since Cloudflare has no OIDC for GitHub); Cloudflare building every push
  (no test gate). This also picked Pages over Workers static assets.
- **Q25 SHA-tagged images and a rollback workflow.**
- **Q26 Smoke check after each deploy and in the keep-alive.**
- **Q27 No reminder for the AWS Free plan's end;** the operator handles it.
- **Q28 No analytics.**
- **Q29 Defaults:** `www` redirect, `privacy@` forwarding, Resend sender, screenshot domain, PLAN.md row.
- **Email, asked on the side:** Email Routing allows about 200 addresses per domain and only forwards; Resend sends
  from any address at the verified domain. Replies from `privacy@` go out from the operator's own address.
