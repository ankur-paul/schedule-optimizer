# AI assistant (discussion, 24 Oct 2026)

Roadmap idea #5, with idea #6 reworked. Seven rounds of questions. The plan below is what came out of them, and the
grilling notes at the end record the reasons and the options turned down.

## Plan

### What changes for the user

- **An *Assistant* button in the header** opens a side panel on every step. It answers questions about the app
  ("how do I lock a class?") and about the user's own timetable ("why can't this be built?", "why is CSE-3A's lab
  unplaced?", "where does the score of 34 come from?", "when is T7 free on Tuesday?").
- **Read-only.** The assistant changes nothing. Changing data and timetables is a later pass (#5b).
- **Who can use it:** signed-in members of an institute (admin, editors and viewers alike) whose institute has
  access. Access comes from a **trial coupon** (below). The panel shows one of these states:
  - **Signed out:** "Sign in to use the assistant".
  - **Signed in, no institute:** create or join an institute first.
  - **Locked, admin:** what the assistant does, a coupon box, and *Request a trial coupon*.
  - **Locked, editor or viewer:** the same description and "Your institute's admin (name, email) can unlock it".
  - **Open:** the chat, with "143 questions left · until 23 Nov" in the header, amber under 20 questions or 3 days.
- **When the allowance runs out or expires**, the panel goes back to the locked state and keeps the chat on screen.
- **Which institute:** the one the working copy is linked to (*Open from institute* or *Save online*); otherwise a
  picker in the panel, hidden when the user belongs to only one institute.
- ***Ask about this*** on problem cards (*Can't be built* causes, *Couldn't finish*, unplaced-cause groups, data
  checks) opens the panel with that card's details attached to the question. The links show only to signed-in users.
- **Answers link to the help** (`/help/generate#no-room`) and name the screen involved.
- **Language:** it answers in the language the user writes in; the UI stays English. It politely declines questions
  that aren't about the app or the user's timetables.
- **Chat history** stays in the browser tab. *New chat* clears it. After every 20 questions the chat is compacted:
  the model writes a summary that replaces the old turns in what is sent, while the panel still shows the whole chat.

### Access by coupon (replaces Razorpay)

- **Razorpay is dropped for now.** There is no paid plan; access comes only from coupons. A paid plan (Razorpay or
  similar) is a possible later idea.
- **A coupon unlocks the whole institute**, and only the admin can redeem it.
- **Each coupon carries a question allowance and a number of days**, chosen when issued (default 200 questions, 30
  days). The days count from redemption. Redeeming a second coupon adds its questions and takes the later expiry; if
  the old access had already expired, its leftover questions are gone.
- **Format:** `LTC-XXXX-XXXX-XXXX-XXXX`, 16 characters from a cryptographically secure generator, without look-alike
  characters (no `0 O 1 I L`), so 80 bits of randomness. Typing is forgiving: lower case, spaces and missing dashes
  are fine.
- **Storage:** only the SHA-256 hash of the normalised code. Each code is single-use and records which institute
  redeemed it, who, and when. Unredeemed codes stay valid until used.
- **Redeeming** goes through a database function that allows 10 wrong tries per user per hour.
- **Issuing:** `cd server && uv run scripts/issue_coupon.py --questions 200 --days 30 --note "tester: GNDEC CSE"`.
  It uses the service-role key, stores the hash, and prints the code once. The operator emails it by hand.
- ***Request a trial coupon*** is a `mailto:` link to `VITE_CONTACT_EMAIL` with the subject "Lattice assistant
  trial" and a body pre-filled with the institute's name and handle and a line asking what they'll use it for.

### How it's built

- **The browser drives the loop; the server makes one model call per request.**
  1. The browser sends the chat so far to `POST /agent`.
  2. The server checks the caller, makes one Claude call and returns the reply.
  3. If the reply asks for tools, the browser runs them over the working copy and sends the results back as the next
     request. Otherwise the reply is the answer.

  The server keeps nothing in memory between requests (the Lambda rule): history comes with each request, and
  allowance, question tracking and usage live in Supabase.
- **The tools run in the browser**, in TypeScript, reusing `causes.ts`, `validator.ts` and `grid.ts`:
  - `overview`: counts, the status (built, partial, can't be built, not generated) and the score per soft rule.
  - `schedule(kind, id)`: a section's, teacher's or room's week.
  - `free_periods(kind, id, day?)`: when a teacher, section or room is free.
  - `problems`: data checks, unplaced classes with their causes, and the *Can't be built* causes.
  - `score_details(rule?)`: where each S1–S4 penalty comes from.
  - `find(text)`: look up a section, room, course or teacher by name or ID.

  The tool definitions live in one file, `shared/agent-tools.json`. The server sends them to Claude and the browser
  type-checks against them, so a client can't add tools of its own. The browser checks each tool input against the
  schema and returns an error result for a bad one.
- **Teacher names never leave the browser.** Before sending, the browser replaces teacher names with their IDs in the
  user's text and in tool results, using the teacher list (the same idea as `withoutPersonalData` for `/solve`). On
  screen, IDs in answers are shown as names again. The history keeps what was sent, unchanged, because the API
  rejects edited history.
- **The model:** Claude Opus 5.5 (`claude-opus-5-5`) at effort `low`, no streaming, at most 8,000 output tokens per
  call, with the API's server-side refusal fallback on. The system prompt holds the instructions and **the full
  help text** (`web/src/help/*.md`, image lines dropped), marked for prompt caching. Prompt caching means Anthropic
  stores this fixed opening part of the prompt between requests. A repeated prompt then costs about a twentieth as
  much, and every user shares the cache while the help is unchanged. There is no help tool.
- **Checking the caller (server):**
  - The server confirms the login token with Supabase Auth and gets the user ID.
  - It calls `agent_begin` with the service-role key. That database function checks, for that user:
    - membership of the institute and acceptance of the current policy version;
    - access not expired, and questions left when a new question starts;
    - this month's spend under `AGENT_MONTHLY_USD`;
    - the question's own limits.

    It charges one question when a new one starts.
  - After the Claude call, `agent_record` writes the usage row.

  Only the service role may run these two functions, so a browser can't fake usage or skip the checks.
- **Limits per question, kept in the database** so a modified browser can't get around them: at most 9 model calls
  (8 tool rounds plus the answer), at most one compaction, and nothing after 15 minutes. After 8 tool rounds the
  last call is made without tools, so the model answers with what it has or says it couldn't finish.
- **Usage rows:** one per model call. Each row holds the question, institute, user, time, model, kind (turn or
  compaction), input, output, cache-read and cache-write tokens, and cost in US cents. The text of questions and
  answers is never stored. The questions that start rows count against the allowance. The rows add up to the monthly
  spend, and they give real cost-per-question numbers for any later paid plan.
- **Deploy:** `/agent` is a route on the existing FastAPI app. At deploy time the same container image runs as a
  **second Lambda function** with about 512 MB of memory, so waiting on Anthropic isn't billed at the solver's 3–7 GB
  and chats don't take the solver's concurrency slots. The web app reaches it through `VITE_AGENT_URL`.

### Cost

- **Estimate:** roughly 5–15 US cents per question on Opus 5.5. `agent_eval.py` measures the real figure.
- **Allowance:** each coupon's allowance caps what one institute can spend.
- **`AGENT_MONTHLY_USD`** (default $10) stops the assistant for everyone once this month's recorded spend reaches it.
  The panel then says it is paused until next month.
- **A spend limit on the Anthropic account** is the final backstop.

### Privacy

- **Policy v3**, drafted by Claude and approved by the user before it ships, like v2. It names Anthropic as a
  processor that receives questions and the timetable details the assistant looks up, with processing in the US. It
  says teacher names are replaced by IDs, that we don't store chats, how long Anthropic keeps API data (checked while
  drafting), and what the usage and coupon records hold.
- **Every signed-in user accepts it again** (the rule from the privacy pass). `agent_begin` refuses users who haven't
  accepted the current version.

### Testing

- Pytest for `/agent` with a fake Claude client, with no network or cost: the caller checks, the limits, the tool
  definitions sent, the cost sums.
- Vitest for every browser tool, the name masking and the panel's pure logic.
- Supabase tests for the coupon and usage functions, like `test_rls_*`.
- `cd server && uv run scripts/agent_eval.py` asks about 15 fixed questions about the sample college through the real
  API and prints the answers, calls and cost. It costs real money, so it is run by hand before release and is never
  part of `npm test` or `pytest`.

### Env vars and services (copy to the roadmap's deploy list)

- **Server:**
  - `ANTHROPIC_API_KEY` (secret).
  - `AGENT_MONTHLY_USD` (default 10).
  - `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` (secret). These are now needed at runtime, not only for tests.
- **Web:** `VITE_AGENT_URL`, which defaults to `VITE_SOLVER_URL`.
- **A second Lambda function** from the same image, about 512 MB, for `/agent`.
- **CORS** allows the `Authorization` header from the web app's origin.
- **The image** includes `web/src/help/*.md` and `shared/agent-tools.json`.
- **Anthropic account:** set a monthly spend limit, and check API data retention for the policy.

- Payments.
- An operator page for coupons.
- Per-user limits inside an institute.

- The assistant on the public timetable page.

## Grilling notes

- **Q1 The agent is next.** Rejected: the walkthrough (#7, last so it tours the finished UI) and deploy (#8, at the
  end by the 22 Oct decision).
- **Q2 Read-only first.** Rejected: read and write together; write-only command bar. Read-only answers cover the
  hardest part of the app (causes, unplaced classes, the score) and give cost data before the agent gets any power.
- **Q3 The browser's working copy.** The agent sees what the user sees, unsaved edits included. Rejected: the
  online version in Supabase, which can be behind. This replaces the online-data pass's assumption (Q1 there) that
  the agent would edit the stored version on the server.
- **Q4 Signed-in institute members, any role.** Limits and access are per institute. Viewers may use it because it
  changes nothing.
- **Q5 Claude Opus 5.5 at low effort.** Prices per million tokens, input / output: Opus 5.5 $4 / $20, Sonnet 5.5
  $2 / $10, Haiku 5.5 $0.10 / $0.50. Model and effort get tuned from the eval numbers.
- **Q6 Teacher names replaced by IDs** before anything is sent, so the model never sees a real name.
- **Q7 History in the browser only.** No chat table, nothing for deletion requests, a short policy line.
- **Q8 A side panel on every step,** plus *Ask about this* on problem cards next to the help links.
- **Q9 Tools run in the browser.** Reuses the TypeScript logic and sends the least data. Rejected: sending the
  whole working copy (up to 2 MB) and porting the cause and score logic to Python.
- **Q10 A route on the existing FastAPI app, no streaming.** Python on Lambda doesn't stream without an adapter.
- **Q11 and Q32 Checking the caller.** First proposed: one database function called with the user's own token, and
  no service-role key on the server. Changed in Q32: a function a user's token can call, the user can call too, so
  usage rows written that way could be faked, for example a huge cost that trips the monthly stop for everyone. The
  server now confirms the user with Supabase Auth and calls service-role-only functions with that user ID. Roles
  are still checked in the database. Rejected: a fixed cost estimate per call with real numbers only in logs.
- **Q12 No AI without payment.** Rejected: a free daily allowance per institute.
- **Q13 Bump the policy to v3** for everyone. Rejected: a separate consent at first use.
- **Q14 Full help text in the cached system prompt.** The user asked why not send the help links. The API model
  can't open links by itself; a fetch tool would only work once the site is public. Rejected: a `read_help` tool.
- **Q15 Answer in the user's language;** decline off-topic questions.
- **Q16 Access by trial coupon,** stored as hashes, chosen by the user over an allow-list environment variable.
  Testers go through the same path as anyone else.
- **Q17 Locked users see the access screen** with *Request a trial coupon*. Rejected: hiding the assistant until
  payments exist.
- **Q18 Razorpay dropped for now.** No KYC or merchant question. Without real payments, the worry about Vercel
  Hobby being non-commercial goes away for now.
- **Q19 A coupon unlocks the institute; only the admin redeems.** Matches the auth pass ("only the admin buys,
  editors spend"). Rejected: per-user coupons.
- **Q20 An allowance plus an expiry per coupon,** default 200 questions over 30 days. `AGENT_MONTHLY_USD` stays as a
  global backstop.
- **Q21 16-character codes, hashed, single-use, 10 wrong tries per user per hour.**
- **Q22 A script issues coupons.** Rejected: an operator page, which would need a site-operator role.
- **Q23 `mailto:` to request a coupon.** Rejected: a request form with a table and outgoing email.
- **Q24 One button, one panel,** whose content depends on the state. No new page or route.
- **Q25 The allowance in the panel header,** amber when low; the chat stays on screen when access runs out.
- **Q26 Six read-only tools,** and *Ask about this* attaches the card's details.
- **Q27 Usage rows hold numbers only,** never the text of the chat.
- **Q28 Fake-client tests always; a real-API eval by hand** before release.
- **Q29 and Q31 Caps:** 8 tool rounds per question and a maximum output length. The user suggested compacting the
  chat instead of forcing *New chat* after 20 questions. The compaction call doesn't count against the coupon.
- **Q30 Five tickets.** Reordered while writing the plan: the policy (T39) now comes before the panel (T40).
- **Lambda check (asked after Q31):** it works. The server is stateless, a Function URL has no 30 s cut-off, there is
  no streaming, and a Lambda outside a VPC reaches Anthropic and Supabase. The agent runs as a second, small function
  from the same image, so it doesn't share the solver's memory size or concurrency.
- **Found while planning:**
  - The server checked no logins before this pass.
  - `has_current_consent()` reads `auth.uid()`, which is empty when the server calls with the service role, so the
    agent functions need a variant that takes the user ID.
  - Teachers have no availability data, so "when is X free" is answered from the generated timetable.
